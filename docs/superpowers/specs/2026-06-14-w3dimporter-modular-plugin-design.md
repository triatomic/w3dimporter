# W3D Importer — Modular Source + Packaged `.mzp` Plugin

**Date:** 2026-06-14
**Status:** Approved (design)
**Repo home:** `triatomic/w3dimporter` (local clone `_pr_workspace/w3dimporter`)

## Problem

`w3dimporter.ms` (the editing copy `W3dTools/src/w3dimporter-v20.ms`) has grown to
**6,486 lines** in a single file. It is hard to navigate, hard to review, and the
single-scope layout makes the file fragile (documented forward-declaration /
autoload scoping gotchas). The user wants it (a) split into multiple files and
(b) installable like a real 3ds Max plugin (menu entry, clean install).

## Goals

- Split the source into focused, single-purpose modules a person can hold in
  their head.
- Ship as a proper plugin: a macroScript in a **W3D Tools** menu, installed via a
  drag-drop `.mzp`.
- **Change no import/export behavior.** This is a pure source-reorganization plus
  a launch-mechanism change.

## Non-Goals

- No rewrite to a compiled C++ `.dlu` plugin (considered and rejected: ~6.5k lines
  of working MAXScript, months of risk for little user-visible gain).
- No new features, no logic changes to chunk reading, scene building, materials,
  or UI.
- No change to the public release artifact's name or load semantics
  (`w3dimporter.ms` keeps shipping as a single file).

## Resolved Design Decisions

1. **Plugin target:** Packaged MAXScript module (not compiled C++, not a bare
   file split).
2. **Runtime model:** Edit as modules, **build-concatenate to a single
   `w3dimporter.ms`**. The runtime is still one file, so cross-file scoping /
   forward-declaration failures *cannot occur*, and the release surface is
   unchanged.
3. **Auto-open behavior:** The plugin opens **only from the menu / macroScript**.
   The current tail that auto-opens the dialog on evaluation is removed.
4. **Home:** All new artifacts (`modules/`, build script, `.mzp` packaging, this
   spec) live in the `w3dimporter` repo. Built `w3dimporter.ms` stays at repo
   root, as today.
5. **Module granularity:** ~9 modules is the cap — the grouping below, not finer.
   One concern per file, but no further subdivision (finer than this is overkill).
6. **Keep the legacy single-script file.** The pre-split monolithic script is
   *retained* (archived), not retired. See "Legacy file" below.

## Architecture

### Source layout

Modules are **contiguous slices of the current file**, cut only at top-level
`fn` / `struct` / `rollout` boundaries. No code is rewritten or reordered; the
concatenation reproduces the current top-to-bottom order exactly. Order is
load-bearing in two places that the slicing preserves: structs precede the
readers that construct them, and the material builders (`buildW3DMatl` at
line 1520) precede `cfW3DImporter`, which calls them.

```
w3dimporter/
  modules/
    00-header.ms        banner, version, w3di namespace, forward-decl globals,
                        w3dUniqueNodeName, w3dMatlAvailable          (~1–84)
    01-structs.ms       all data-model structs (hierarchy/anim/mesh/hlod) (~86–359)
    02-chunkreader.ms   low-level read helpers + every Read* fn,
                        incl. ReadHLod                              (~360–1519)
    03-materials.ms     buildW3DMatl, buildMultiPassW3DMatl + helpers (~1520–pre-core)
    04-import-core.ms   cfW3DImporter scene builder (the large one)
    05-ui-renegade.ms   rltRenegade advanced dialog                 (~4926–5422)
    06-preferences.ms   W3D_Importer_Init struct + W3DPreferences   (~5423–5968)
    07-mix.ms           Mix_File .mix archive browser               (~5969–6257)
    08-ui-main.ms       rltMain + rltMainMenu                       (~6258–end-of-defs)
    99-register.ms      W3DImporterInit.init() + macroScript registration
  build-w3dimporter.ps1 concatenates modules/*.ms (sorted) -> w3dimporter.ms
  w3dimporter.ms        BUILD OUTPUT (committed; release artifact)
  packaging/
    w3dimporter.mzp.txt mzp manifest / install script source
  docs/superpowers/specs/2026-06-14-w3dimporter-modular-plugin-design.md
```

Exact line boundaries are finalized during plan writing from the live top-level
definition positions; the table above is the intended grouping.

### Build step

`build-w3dimporter.ps1`:

1. Reads `modules/*.ms` in lexical (numeric-prefix) order.
2. Prepends a generated banner:
   `-- AUTO-GENERATED by build-w3dimporter.ps1 — edit modules/, not this file --`.
3. Concatenates verbatim (preserving each module's bytes; only joins with a
   newline between files) into `w3dimporter.ms` at repo root.
4. No transformation of module content — MAXScript is whitespace-insensitive, so
   a dumb ordered concatenation is sufficient and safe.

The script runs in PowerShell (native to this environment, no Max required, CI-
friendly).

### The "plugin" surface

`99-register.ms` replaces the current auto-launch tail with:

```maxscript
W3DImporterInit.init()
macroScript W3D_Importer
    category:"W3D Tools"
    toolTip:"W3D Importer"
    buttonText:"W3D Importer"
(
    on execute do
    (
        try (destroyDialog rltMain) catch ()
        createDialog rltMain menu:rltMainMenu
    )
)
```

The `.mzp` (a renamed zip containing `w3dimporter.ms` + an `mzp.run` install
script) copies `w3dimporter.ms` into the user `scripts/` directory, evaluates it
(registering the macroScript), and adds a **W3D Tools > W3D Importer** menu item.
Drag-dropping the `.mzp` onto a Max viewport installs it.

## Regression Guard (how we prove behavior is unchanged)

The reorganization is validated mechanically, not by eyeball:

- Concatenating `modules/00-header.ms … 08-ui-main.ms` (i.e. everything except
  `99-register.ms`) must equal the current single-file definitions **byte-for-
  byte**. The only intended delta from today's file is the launch tail, which is
  isolated in `99-register.ms`.
- A `diff` of `build output (minus 99-register tail)` against the v21.4 editing
  copy must show **zero** differences in the definition body. This guarantees the
  split moved bytes around without altering a single statement.
- Manual smoke test in 3ds Max after building: install the `.mzp`, open via the
  **W3D Tools** menu, import a known `.w3d` (including the duplicate-object file
  from the `~NN` fix), confirm identical results to the pre-split script.

## Source-of-Truth / Dependency Note

The content to be split is `w3dimporter.ms` at **`v21.4`**, which includes the
`~NN` duplicate-object naming fix. **Resolved:** that fix has been merged to
`main` (fast-forward, `fix/importer-duplicate-name-numbering` → `main`, local
only / not pushed). `main` is therefore the correct v21.4 baseline the build
output must reproduce. The modularization is based on `main`.

## Legacy file

The pre-split monolithic script is kept, not deleted. On split, the current
`w3dimporter.ms` is preserved as a frozen reference copy
(`legacy/w3dimporter-v21.4.ms`) committed alongside the new `modules/`. It is a
read-only fallback and the byte-for-byte comparison target for the regression
guard; it is not loaded or shipped. The generated `w3dimporter.ms` at repo root
remains the live release artifact.

## Risks & Mitigations

| Risk | Mitigation |
|---|---|
| A module split lands mid-statement and breaks the build | Cut only at top-level `fn`/`struct`/`rollout` boundaries; byte-reproduce guard catches any drift. |
| Removing auto-open breaks someone's startup workflow | Documented; macroScript + menu is the supported entry. `.mzp` install wires the menu so it's discoverable. |
| Editing copy (`W3dTools/src`) and repo drift apart | After this lands, the editing copy points at the repo build output. Captured as a follow-up; the legacy single-script file is kept regardless. |
| Future edits bypass `modules/` and hand-edit `w3dimporter.ms` | Generated banner warns; reviewers reject direct edits to the build output. |

## Out of Scope / Follow-ups

- Pointing the `W3dTools/src` editing copy at the repo build output (the legacy
  single-script file is kept per the decision above; this is just about which
  copy is edited day-to-day).
- Optional CI check that `w3dimporter.ms` is up to date with `modules/`.
- Any menu/toolbar polish beyond a single **W3D Tools > W3D Importer** entry.
